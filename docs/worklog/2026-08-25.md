## OmniVoice FlashInfer RTX 5090 compatibility correction

- CUDA 12.8 recipe는 RTX 3090에서 동작했지만 RTX 5090 model warmup에서 실패했다. 설치된
  FlashInfer 0.6.15의 SM12 architecture normalization 경로가 CUDA 12.9 이상을 요구한 것이 원인이며,
  Blackwell 전체나 CUDA 12.8 일반 지원 여부와는 구분한다.
- target을 `evelyn-omnivoice-tts:recipe-e8151492550b`로 갱신했다. pinned CUDA 12.9.2 base,
  `libnpp-12-9=12.4.1.87-1`, Torch/Torchaudio 2.8.0+cu129, TorchCodec 0.7.0+cu129,
  FlashInfer Python/Cubin 0.6.15.post1과 JIT cache +cu129를 사용한다.
- image `sha256:ec6efba2dbcd9c79a3d0666d801f635d54cab4ea4a35272d669f0ab23e27a5ae`를
  실제 RTX 5090 `(12, 0)`에 올렸다. health는 CUDA 12.9, `flashinfer_cuda_graph`, JIT off,
  2/4/8초 graph bucket, concurrency 1과 12-step을 확인했고 host/container GPU UUID도 일치했다.
- image 내부 TorchCodec import와 package metadata, benchmark self-test/Python compile,
  관련 runtime 계약 76개와 subtest 38개, diff check가 통과했다.

## Main LLM latency end-state design

- 임시 filler나 단일 component 수치 개선이 아니라 `post-STT -> 검증된 첫 답변 PCM -> playback` 전체를
  최적화하는 목표 구조를 승인하고 `docs/MAIN_LLM_LATENCY_TARGET_ARCHITECTURE.md`에 기록했다.
- 목표 설계는 content-free stage trace, 공용 Prompt ABI, terminal-drain과 second-suffix cache proof,
  Main realtime GPU lane, irreversible speech commit, bounded TTS overlap과 fixed evaluator 기반
  LLM-to-harness candidate loop를 포함한다.
- production harness/evaluator/authority의 자기 수정과 자기 승격은 금지하고, allowlisted isolated 실험과
  exact 사람 승인 canary/rollback을 분리했다.
- 이 checkpoint에서는 runtime code, Compose 배치와 live service를 변경하거나 실행하지 않았다. SLO와
  GPU0 Main+TTS/GPU1 ingress 배치는 구현 사실이 아니라 다음 단계에서 검증할 target/candidate다.

## Main LLM native SM120 root-cause correction and diagnostic live run

- 기존 llama.cpp CUDA library에는 RTX 5090용 cubin이 없고 `sm_52` PTX만 들어 있었다. graph on/off 모두에서
  첫 resident history append가 약 11.3초 지연됐고 display/TDR event는 없었다. 이 증거에 따라 first-use PTX
  JIT를 원인으로 좁히고, 기존 build를 덮지 않은 side-by-side CUDA 12.9.2 `120a-real` build를 만들었다.
  정적 검증은 CUDA compile target과 cubin이 `sm_120a` 하나이고 PTX가 없으며 server version/commit
  identity가 고정됐음을 확인했다.
- Docker Main runtime base를 pinned CUDA 12.9.2 runtime으로 맞췄다. optional
  `EVELYN_MAIN_LLM_BUILD_DIR`은 llama.cpp root 아래의 별도 build만 Main/GPU0의 `/llama/build`에 read-only로
  겹쳐 mount한다. GPU1 Router/Sub build는 바꾸지 않는다. fixed lab worker는 선택 build의 root containment,
  reparse boundary, `bin/llama-server`와 content hash를 실행 전에 검증한다.
- Fast와 Core/Discord warmup은 실제 production이 사용하는 `clean_text` canonical system prefix의 Prompt ABI를
  미리 계산해 `expected_prompt_abi_ids`로 전달한다. warmup compiler 결과가 다르면 HTTP 전에
  `llm_warmup_prompt_abi_mismatch`로 닫고, Bot readiness는 cache proof와 `productionPromptMatch=true`를 함께
  요구한다. 개인 prompt 원문은 evidence나 문서에 남기지 않는다.
- native graph-off diagnostic은 strict cache `33/33`, validity failure `0`, clean cleanup이었다.
  first-after-warmup은 first PCM `824.9ms`, TTFT `233.252ms`, prompt eval `230.2ms`, cache
  `355/405`이었다. resident 5회의 first PCM은 `292.1/239.9/237.2/246.9/228.0ms`
  (p50/p95 `239.9/292.1ms`), TTFT는 `57.301/36.539/38.298/43.862/23.660ms`
  (p50/p95 `38.298/57.301ms`)였고 11.3초 tail은 재현되지 않았다. idle 뒤 first PCM은
  `429.3ms`, TTFT `211.775ms`, prompt eval `205.7ms`, cache `556/557`이었다.
- 동일 backend exact-payload 진단 TTFT는 graph-off cold/capture/resident/idle
  `654.59/19.58/21.17/159.95ms`, graph-on `380.49/14.93/16.21/246.83ms`였다. 서로 다른 leg에서
  우열이 갈려 graph 기본값을 고를 증거는 아니다.
- 이 first-PCM run은 이후 발견된 실제 TTS 합성 readiness 정정 전 표본이므로 production SLO나 TTS-ready
  end-to-end 승격 근거로 사용하지 않는다. production graph/SWA/ubatch 기본값과 automatic promotion은
