# 2026-08-24 Worklog

## Harness cancellation and approval boundaries

- Task-loop worker/stage/test가 cancellation을 삼키거나 deadline·wall grant가 끝난 뒤 결과를 반환해도
  normalize, approval과 effect dispatch 전에 currentness를 다시 검사한다. task approval wire v2는 exact
  task/stage/path/SHA와 유한 TTL을 결박하고 만료 뒤 cancel은 허용하되 apply는 닫는다.
- Discord text mutation은 claim 뒤의 각 history/session/terminal 단계에서 exact guild epoch를 재검증한다.
  reset 뒤 stale turn은 새 history, delivery나 completion을 만들지 않는다.
- STT batch와 streaming/local bridge의 caller가 반복 취소돼도 이미 시작한 physical worker와 cleanup을
  shield-drain하고, shared inference/transition lock은 실제 물리 작업이 끝날 때까지 유지한다.

## Durable outbound effect recovery

- Discord command, search follow-up과 assistant autonomy follow-up/ping/오류 알림은 기존
  `ConversationIngressRecoveryJournal`을 사용해 durable intent, exact source/action-run ID, delivery phase,
  Discord receipt, canonical continuity와 terminal completion을 분리한다. 모호한 timeout/cancellation은
  successor effect를 fail-close하고 definitive pre-effect 4xx만 안전한 retry로 남긴다.
- Search follow-up은 private prepared answer를 journal에만 보존하고 공개 상태에는 고정 코드와 count만
  투영한다. exact Discord receipt와 unique source/delivery pair, pre-send generation baseline을 모두
  확인한 경우에만 restart adoption한다. 채널 조회 증거는 source message를 exact reply/reference한 유일한
  bot-authored same-content message여야 하며, 0개는 안전한 재전송, 중복·무참조·다른 source는 fail-close한다.
  unresolved entry는 capacity 때문에 축출하지 않으며 journal complete를 선택적 memory/cognitive
  projection보다 먼저 기록한다.
- 최초 search recovery는 restored snapshot에서 프로세스당 한 번만 수행한다. recovery가
  `COMPLETE`가 되기 전에는 Discord text와 실제 voice turn admission, voice worker/Control Page/Local mic
  시작을 차단한다. 실패·취소는 `FAILED`로 고정해 이후 live state를 recovery 근거로 재사용하지 않는다.

## Autonomy authorization and privacy

- 다른 autonomy source의 `delivery_inflight|delivery_ambiguous`가 남아 있으면 successor를 차단한다.
  반복 cycle/executor 오류는 정상 cycle 전까지 한 episode로 묶어 고정된 private-free 문구를 최대 한 번만
  알린다.
- durable outcome audit에는 action별 allowlist에 포함된 evidence code만 기록한다. sanitized step result의
  `verified`는 허용된 step domain/action과 strict outcome verifier로 다시 계산하며 caller boolean을 신뢰하지
  않는다.
- 외부 effect 뒤 memory-deletion integrity 오류가 나도 exact outcome audit, engine state/cursor와 ping fence를
  먼저 내구화한 뒤 fixed-type 오류만 재전파한다. raw 예외나 private 값은 result·audit·status에 넣지 않는다.

## Post-STT latency measurement

- 기존 runtime이 모두 내려간 상태에서 current dirty source를 일회성 exact SHA 이미지로 빌드하고 Main,
  Router, Sub, Bot API와 OmniVoice만 기동했다. 측정 입력·continuity·logs는 전용 임시 Docker volume으로
  격리했으며 Discord, microphone, STT, Vision과 Minecraft는 기동하지 않았다.
- Bot API NDJSON request 시작부터 Main 첫 delta·첫 문장·완료를 재고, 첫 문장 event 즉시 production과 같은
  OmniVoice `clone:evelyn`, 16-step PCM request를 시작했다. 1 cold, 3 discarded warmup, 10 warm measured를
  사용했고 모든 measured response는 동일한 11자 한 문장이며 오류는 0이었다.
- warm p50/p95는 첫 delta 353.8/415.7ms, 첫 문장 374.2/435.8ms, TTS 자체 첫 PCM
  427.6/446.2ms, STT 제외 request→첫 PCM 804.0/873.5ms였다. cold request→첫 PCM은 2,545.9ms였다.
- 이 값은 Bot API policy/context/Main과 OmniVoice 첫 PCM까지의 core post-STT latency다. 실제 Windows
  speaker buffer, Control Page proxy와 Discord playback은 포함하지 않았으므로 사용자 청취 E2E로 표현하지 않는다.
- 측정 뒤 Bot API를 원래 bind-mount의 정지 상태로 되돌리고 Main/Router/Sub/TTS를 정지했으며, 임시 volume과
  override를 제거하고 Docker Desktop을 종료했다. 관련 port는 모두 닫혔고 GPU1은 0MiB, GPU0은 시작 전 수준인
  약 3.6GiB로 복귀했다.

## Local Fast Main cold warmup

- Bot API가 서버 startup을 막지 않는 cleanup task로 정확한 `FAST_MAIN_LLM_SYSTEM_PROMPT`를 Main LLM에
  `cache_prompt=true`로 warmup한다. 기존 Fast inference와 같은 persistent HTTP session을 재사용하고 실패는
  content-free 상태로 표시한 뒤 재시도한다.
- Bot API `/health`와 core diagnostic `ok`는 warmup에 결박하지 않는다. 대신 Control Page의
  `chatReady`/`voiceReady`/chat input과 실제 local chat·chat-stream·voice admission은 warmup 완료 전 닫고,
  완료 뒤에만 연다.
- production compile과 warmup/source-health/Fast handler·ingress focused 163개, subtests 25개가 통과했다.
  Docker, GPU, microphone, Discord 등 live 서비스는 실행하지 않았으므로 cold first-turn 개선폭은 아직 재측정 전이다.
