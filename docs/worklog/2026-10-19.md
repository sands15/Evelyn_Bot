### 첫 원격 실행과 자료 경계 수리

- 선행 커밋 `59fe6654`와 보호장치 `662aeb594268c1735cae0583818a657563f8b15b`를 새 브랜치에 push했다. main은 기준 커밋 그대로이며 기존92커밋 포함 수0이다.
- [첫 실제 CI](https://github.com/sands15/Evelyn_Bot/actions/runs/39149142330)는32검사·컴파일 후 정상 JVM 단계에서 `catalog_hash`로 FAIL했다. 의도한 오답 단계는 NOT_RUN이므로 오답 검출 성공으로 세지 않는다. 첫 artifact `12143804203`와 ZIP SHA256 `c4f4ee502c1c3399bab6a7aee811baaa66d7f1ea13dd1cfb74894be65896ace9`를 보존했다.
- 실제 Git 체크아웃을 소유 임시 폴더에 재현해 block/item 자료가 LF→CRLF로 변환되고 같은 JVM 실패가 발생함을 확인했다. 다른 두 자료의 원본은 CRLF인데 commit 과정에서 LF로 바뀌어 있어 일괄 LF 변경도 올바른 수리가 아니다.
- 해시 고정 JSON4개의 Git text 변환만 끄고 원본 바이트를 index에 보존했다. 공식 자료 해시·제품 loader 기준은 바꾸지 않았다. 새 체크아웃의4개 지문이 원본과 모두 일치하고, 기존 실제 Java loader4종과 정상/변조 메뉴 경계를 묶은3검사 PASS다. 관련 자료 경계를 한꺼번에 확인한 뒤에만 원격 실험을 재개한다.
- autocrlf true/false 각각의 별도 체크아웃4개가 모두 원본 지문과 같았다. 실제 체크아웃 리소스를 사용한 로더4종·정상 메뉴 PASS 및 동일 변조 exit1/공식 count 불일치/성공 보고 없음도 확인했다. 동일 검토자가 index 바이트를 제품 pin과 독립 대조해 내용·기준 변경 없음과 수리 범위를 확인했다. CRLF 원본 자료에 대한 공백 검사는 CR-at-EOL만 정상으로 인식하고 다른 공백 검사는 유지한다.
