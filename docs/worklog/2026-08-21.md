# 2026-08-21 Worklog

## Bounded LLM collaboration loop

- 명시적 `/작업 <목표>`를 기존 Router → registered skill/FastAction → Main 경로에 연결했다. task loop는
  최대 6 task-step·120초이고, 판단이 필요한 단계에서 Qwen worker가 typed step 하나를 제안하면 executor의
  관측·검증 receipt를 다음 판단에 돌려준다.
  `completed`, `awaiting_approval`, `blocked`, `uncertain`, `cancelled`, `budget_exhausted`는 서로 다른 terminal이며
  noncompleted 결과는 Main이나 worker 자유문장으로 성공 승격하지 않는다.
- automatic 권한은 server-attested Control Page의 bounded workspace list/search/read/diff, runtime status와
  사용자가 명시한 public web search로 제한했다. read-only 완료는 closed single-operation grammar, exact
  path/query/scope/recursive args와 model-visible typed evidence를 요구한다. list/search/diff는 `truncated:false`,
  read는 아래의 same-SHA 0→EOF chain이어야 한다. goal의 quoted whitespace는 보존하고 web 불필요/금지 표현은
  outbound auto 권한으로 해석하지 않는다. 다른 surface,
  private/runtime roots, arbitrary shell, delete/auth/push/deploy/external send와 service·Docker·Minecraft effect는
  자동 허용하지 않는다.
- Host의 list/search/diff는 capacity-one worker로 분리했다. oversized/unreadable/skipped search와 untracked 또는
  incomplete diff는 `truncated:true`로 닫고, complete diff는 tracked path의 `HEAD→worktree`에 결박한다.
- workspace read queue를 protocol v2로 올렸다. Host는 최대 2KiB UTF-8 청크를 evidence/transport 각각 3,999자
  이하로 줄여 반환하고, runtime은 exact path/offset/expected full SHA의 다음 청크만 받는다. 완료는 0→EOF
  same-SHA/byte-count 연속성과 합친 content SHA를 다시 검증한다. exact initial read, receipt가 유일하게 정한
  continuation과 post-apply verification read는 runtime이 typed transition으로 직접 실행하고, 판단이 필요한
  단계만 Qwen worker에 남긴다. 기본 6 task-step에서는 terminal transition을 남겨야 하므로 최대 5청크이며 escaping이
  적을 때 약 10KiB가 상한이며 초과는 성공으로 말하지 않는다.
- Qwen이 `workspace_edit` 인자를 mode와 일치하는 단일 `create|replace` envelope 또는 create의
  `path/content` 형태로 반환한 실환경 사례를 재현했다. 전자는 exact matching일 때만, 후자는 기존 파일을
  덮어쓰지 못하는 create로만 정규화한다. 그 밖의 malformed edit args는 behavioral sandbox 요청으로 오인하지
  않고 typed worker observation으로 돌려줘 다음 판단에서 수정하게 하며 Host mutation은 호출하지 않는다.
- Windows read/stage/apply는 project root부터 target parent까지 no-reparse directory handle을 작업 끝까지 고정한다.
  실제 Windows test에서 pin 중 ancestor rename이 거부되고 release 뒤 가능함을 확인했으며, pin/path identity 실패는
  typed fail-closed 결과로 고정했다. text/voice task route는 preface·일반 short-circuit·specialist 실행을 건너뛰고
  registered task skill만 호출한다. `None`·empty·echo·malformed 결과는 Main 전에 `TASK_LOOP_INVALID_RESULT`로
  차단한다. 이 시점에는 유효한 read-only completed가 Main을 한 번 거쳤지만 아래 deterministic finalizer 증분에서
  Main 자유문을 terminal claim 경계에서 제거했다.

## Candidate test and exact approval

- 단일 UTF-8 file create/replace를 Host에 stage하고 full diff, base/candidate SHA, git status, target identity와
  dirty-base 확인을 30초 one-use approval에 결박했다. Windows conditional exchange는 ADS와 concurrent save를
  fail-closed하며 cleanup ambiguity는 `recovery_required`로 남기고 자동 재시도하지 않는다.
- exact path와 quoted old/new literal이 목표에 적힌 content edit만 apply 뒤 same-path candidate SHA read로
  완료한다. behavioral candidate는 frozen Git-tracked snapshot과 exact overlay만 fixed Bot API image의 bounded
  no-network/read-only/low-privilege sandbox에서 선택한 test로 관찰한다. failed target은 revised candidate에서도
  전부 다시 실행한다.
- candidate가 runner 결과를 흉내낼 수 있으므로 sandbox receipt는 항상 `semanticVerified:false`인 승인 보조
  관측이다. 사람이 diff를 승인해 적용하고 same-path SHA를 재확인해도 behavioral task는 즉시
  `workspace_behavior_outcome_unverified`로 끝나며 자동 재시도하거나 해결 완료를 주장하지 않는다.
- container나 project-owned snapshot cleanup이 불확실하면 현재 Host 수명 동안 sandbox readiness를 latch-off한다.
  active harness·approval·authority·evaluator와 direct trust-cone 파일은 task edit에서 차단한다.

## Approval and cancellation race hardening

- pre-consume literal apply가 verified failure를 반환할 때 pending binding을 먼저 지우던 stage leak을 수정했다.
  task loop는 exact Host stage discard를 확인한 뒤에만 pending을 비우며, invalid/uncertain은 outer cleanup이 계속
  소유한다. behavioral apply의 `success|succeeded` alias도 모두 path/SHA와 exact `semanticVerified:false` fence를
  통과해야 한다.
- approval cancel을 manager prepare→Host exact stage cancel→manager complete의 2단계로 바꿨다. waiter는 Host
  결과 전에는 pending이고, completion은 approval/stage/Host instance binding을 모두 확인한다. 잘못된 late apply
  complete는 stored claim을 제거하지 못한다.
- direct `/작업취소`는 exact asyncio task intent가 있는 cancellation만 FastAction `cancelled`로 기록한다. coroutine이
  시작되기 전 explicit cancel도 done callback에서 terminalize하며, 표시 없는 server/shutdown cancellation은 기존
  `failed/background_action_cancelled`와 recovery marker를 유지한다. approval이 `claimed|resuming|cancelling`이면 raw
  task cancel로 Host effect와 경쟁하지 않고 현재 결과 확인 상태를 사용자에게 고정 문구로 알린다.
- source audit에서 Qwen `-np 1`이 inference slot만 직렬화하고 task worker·일반 specialist·Mindcraft를 아우르는
  cross-container admission은 없음을 확인했다. task worker의 6초 total timeout에는 queue wait도 포함된다. 단순
  timeout 증가나 process-local lock 대신 기존 authenticated broker를 단일 bounded FIFO owner로 확장하는 작업이
  P1로 남았다.

## Qwen 단일 admission owner

- task worker, 일반 specialist와 Mindcraft의 production Qwen 호출을 기존 authenticated Bot API broker로 통합했다.
  active 1·waiter 3의 bounded FIFO를 쓰며 queue deadline은 enqueue부터, kind별 inference deadline은 실제 slot
  grant부터 계산한다. queued disconnect는 POST 전에 철회하고 in-flight caller cancel/timeout은 upstream EOF까지
  drain한 뒤 successor를 시작해 late result를 다른 request에 결박하지 않는다. grant 직전 deadline·disconnect·
  abandon·poison도 다시 확인해 같은 event-loop tick의 만료 race를 닫았다.
- Python/Node client는 exact request ID·memory receipt와 bounded frame/trailing/ACK body를 확인한다. consumer parse
  성공 뒤에만 `delivered` ACK하고 Qwen·Router server final memory guard가 실패하면 ACK도 실패한다. ACK 10초는 Python task
  outer budget과 Node 135초 request budget에 포함했다.
- transport timeout/ClientError는 owner를 poison하고 durable `qwen-inflight` marker를 남긴다. Qwen container는
  fail-closed boot command로 atomic epoch를 별도 volume에 쓰며 stale marker는 epoch 교체, content-free health와 epoch 재확인이 모두
  맞아야 제거된다. explicit Compose Bot restart/update는 Qwen restart를 결합하고, plain Docker Bot restart는
  같은 epoch에서 recovery-required로 닫힌다. shutdown은 새 admission을 먼저 poison하고 자연 drain하며 Bot/launcher
  stop budget은 130초다. legacy Voyager의 broker 없는 local action 기본값은 `disabled`로 정리했다.
- broker 집중 20개와 broker+Compose 계약 51개(subtests 12)가 통과했다. 당시 canonical
  `tests/` 전체는 3,987 passed, 22 skipped, 1,120 subtests였고 Python compile, 두 planner JavaScript parse,
  base+benchmark Compose config와 scoped diff check도 통과했다. Docker/GPU/Minecraft/Discord 등 live 서비스는
  실행하지 않았으므로 실제 GPU burst·SIGTERM/hard-crash epoch recovery는 미검증이다.

## Adversarial task/Qwen boundary hardening

- 독립 lifecycle·task-loop·authority 감사를 병렬 수행했다. Qwen health가 probe 중 epoch 변경 또는 active marker와
  mounted epoch 불일치에도 ready를 반환할 수 있던 race를 probe 전후 epoch·owner 재검사로 닫았다. bounded full EOF
  뒤 malformed JSON/HTTP/content 같은 semantic 실패가 global owner와 marker를 poison하던 문제는 invocation-local로
  바꿨고, EOF를 확인하지 못한 transport/oversize 불확실성은 계속 poison한다.
- web automatic grant를 broad imperative regex에서 closed single-operation goal의 exact query extraction으로 줄였다.
  실행 직전 goal과 model query args를 다시 대조하므로 compound·long-distance negation·underbound/different query는
  provider 호출 전에 `task_web_query_not_bound` 또는 approval-required로 닫힌다.
- approved workspace apply가 끝난 직후 manager pending이 사라져 post-read 중 `/작업취소`가 raw task cancel과 false
  `cancelled` terminal을 만들 수 있던 race를 수정했다. `resuming` effect barrier는 background terminal cleanup까지
  exact task에 남고, 후속 approval도 그 사이 시작하지 못한다.
- verified workspace mutation completed는 Core·voice·Fast 모두 Main 자유문을 건너뛰고 적용 receipt와 동일 path/SHA
  post-read에서 만든 fixed bounded outcome만 반환한다. 과장 Main mock이 모든 버그 해결·전체 테스트 통과를 말해도
  호출되지 않는다. 당시 read-only/search completed의 Main 합성은 receipt 밖 자유문 claim 가능성을 P1로 남겼고,
  아래 deterministic finalizer 증분에서 닫았다.
- 집중 회귀는 191 passed, 172 subtests였고 관련 production Python compile과 scoped diff check가 통과했다. 최종
  canonical `tests/`는 3,994 passed, 22 skipped, 1,121 subtests였다. 이 증분에서는 live 서비스를 실행하지 않았다.

## Deterministic task/search finalizer

- completed runtime/read/list/search/diff/web receipt는 producer와 같은 exact key/type/count, non-truncated bound와
  goal-bound args를 Core finalizer에서 다시 확인한다. mutation을 포함해 completed task는 Main·worker summary·history를
  terminal claim 권한으로 쓰지 않는다. semantic review/summarize/explain/compare는 raw read/diff/search receipt만으로
  완료하지 않는다. Fast background action에서 invalid completed receipt는 정상 reply가 아니라 `failed` terminal이 된다.
- task의 authorized web query는 provider normalization을 끄고 exact query로 전송한다. 일반 검색은 typed metadata,
  canonical row와 deterministic renderer round trip이 모두 맞아야 통과하며, 등록형 search→main_synthesis도 같은 metadata를
  전달한다. arbitrary raw search text는 content-free 실패로 닫힌다.
- 외부·파일 증거는 canonical JSON UTF-8의 bounded hex prefix와 total/preview byte·truncation metadata로 표시한다.
  display sanitizer 뒤에도 hex가 보존되고 raw model/OmniVoice tag로 해석되지 않는다. 중앙 AnswerPayload뿐 아니라
  Control Page local TTS와 Fast Local Bridge enqueue도 evidence 없는 고정 spoken summary만 사용한다.
- search-capable Voice SSE는 typed search resolution 전 model delta를 TTS로 보내지 않는다. 결과 있음, 유효한 0건,
  검색/봉인 실패를 별도 상태와 음성 문구로 전달해 실패나 빈 결과를 성공처럼 말하지 않는다.
- 기본 6 step에서 mutation 뒤 full read를 끝내는 파일 크기와 semantic summary/link rendering은 기능 한계로 남는다.
  최종 canonical `python -m pytest -q`는 4,052 passed, 22 skipped, subtests 1,126으로 통과했다. production Python
  compile, scoped whitespace와 독립 flow/rendering 재감사도 통과했다. 이 증분에서는 live Discord·마이크·Docker·GPU
  서비스를 실행하지 않았다.

## Main LLM TTFT source optimization

- production persona/tool 계약을 유지하면서 fixed Fast Main prefix를 1,773자에서 938자로 줄이고,
  startup이 voice/Discord와 Fast Control의 실제 system prefix 둘 다 `cache_prompt=true`로 warmup하게 했다.
- voice/local prompt는 저장 history를 보존한 채 최근 non-system 8개만 사용한다. casual fast turn에는
  memory/runtime state를 넣지 않고 tool/policy가 요청한 턴에만 주입한다. Fast Control의 Main LLM
  `ClientSession`은 재사용하고 app cleanup에서 닫는다.
- Main llama.cpp 구성에 CUDA graph opt, batch 2048, ubatch 1024, cache RAM 8192 MiB와 cache reuse
  설정을 명시했다. benchmark는 client TTFT와 별도로 server `prompt_ms`, processed/cached tokens,
  prefill throughput, prediction throughput, prompt-cache hit ratio를 기록한다.
- 관련 Core/Fast/voice/runtime/Compose/benchmark 251개와 production Python compile, scoped whitespace
  검사가 통과했다. live Docker/GPU/마이크/Discord는 실행하지 않았다. 따라서 2026-08-16의
  422.6 ms p95는 새 코드의 결과가 아니며 실제 개선폭은 승인된 live A/B가 남아 있다.

## Latent async-boundary bug audit

- 여러 실패 증상을 독립 원인 3개로 정규화했다. ingress recovery는 wall clock rollback 때 validator가
  거부할 `recoveredAt`을 쓰던 문제를 journal 범위 안의 논리 시간으로 고쳤다. claim 1000 뒤 restart
  950, 재restart 950 fixture가 entry와 ready/current를 보존한다.
- Local Voice는 playback owner claim이 아니라 exact owner/token의 첫 PCM device write 성공을 barge-in
  source receipt로 사용한다. blocked/failed write는 playback-start나 positive interrupt를 만들지 않고,
  다음 sentence owner는 turn 단위 성공 상태를 재사용하지 않는다.
- Local과 buffered STT runtime은 remote start 중 취소돼도 blocking start를 수거해 반환된 stream ID를
  bounded DELETE하고 원래 cancellation을 재전파한다. 유효한 ID를 포함한 malformed start contract도
  state 생성 전에 DELETE한다. ID를 받기 전 transport loss/hard kill은 server TTL에 의존한다.
- conversation recovery 관련 37개, Local barge-in 31개(subtests 7), voice 전체 752개(skip 5,
  subtests 85), STT start 관련 17개가 통과했다. 최종 canonical `python -m pytest -q`는
  4,058 passed, 22 skipped, 1 warning, subtests 1,126이었다. warning은 Python 3.13 예정의 기존
  `audioop` deprecation이다. production Python compile과 scoped diff check를 확인했고 실제
  Discord·마이크·스피커·STT/Docker 서비스는 실행하지 않았다.
